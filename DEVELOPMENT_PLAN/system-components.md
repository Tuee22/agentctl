# System Components

**Status**: Authoritative source
**Supersedes**: N/A

> **Purpose**: Inventory target capabilities, paths, tools and private resources with a single substantive phase owner.

This inventory describes the artifacts built by each owner's contract. Each present artifact shows its current
manifest owner, and one due to move or to be deleted carries a move note naming the Remaining Work row or ledger
row that moves it; a path marked planned is a deliverable of its owner, not a claim that the file exists
([§ F](development_plan_standards.md#f-system-component-inventory)). The [ledger](legacy_tracking_for_deletion.md)
records standing incompatible shapes. The executable ownership manifest independently censuses every present
file, shared dependency and test, and a consumer inherits the owning capability's input identity.
Each numbered phase document is owned by the phase it describes; the common plan structure and shared
governance contracts belong to governance. A later phase document is not an earlier phase's owned source.
Documents under `documents/` belong to the phase named in their `Owning phase` metadata; later consumers
inherit that owner's current identity through the declared prerequisite chain.
The root agent policies, Git checkout settings, common plan files, and shared source/test/plan directory
entries are governance inputs consumed by the gate for every phase.
Oracle data homes named by requirements are owned by their earliest substantive implementation phase;
later phases that close requirements using the same file are declared consumers. The bootstrap plan and
prerequisite oracles originate in Python bootstrap and are also consumed by the relevant later contracts.
Legacy mutant files whose targets all have the same declared owner belong to that owner. Mixed-target
files need an explicit shared-input migration; a filename prefix is not proof of their ownership.

Every row also follows these ownership rules:

- A mutant is owned by its target's owner. A later phase owns it only when no killer is owned within the target
  owner's closure, and a change of owner of a protected mutant or of its killers' modules is a decision row
  naming the id ([T.M](development_plan_standards.md#tm-adequacy) M1).
- Each test module has one owner, who cites its portable nodes, while a node declared to the `linux-clean` or
  `linux-live` half is cited only by phases whose lanes include that half
  ([T.X](development_plan_standards.md#tx-terms)); a later phase adds nodes and corpus, oracle and
  support rows only to files it owns, apart from the appended rows that
  [§ A](development_plan_standards.md#a-well-ordered-constructive-narrative) A3 allows in the mixed-owner data
  files and beside an amended protected row (D-150).
- Python code that only a foreign family executes, and a foreign-family arm that a later phase would otherwise
  have to edit, is a host-declared module owned by the earliest phase whose lane includes that family and whose
  closure contains every module and native package it needs, reached lazily through `foundation_host`; any other
  foreign-family branch of a Haskell or C source stays with its owner
  as a host-declared region ([T.X](development_plan_standards.md#tx-terms)), and confirmation a lower phase cannot
  observe is owed to a later phase whose lane includes the family
  ([§ A](development_plan_standards.md#a-well-ordered-constructive-narrative), D-140, D-162, D-167).
- A capability never lists a later-owned path. A row names paths owned by or planned for its owning phase, and a
  consumer names the earlier-owned paths it uses in its own Deliverables.

## Per-User Directories

Python supplies bootstrap cache/data/state roots. Haskell derives owned runtime subdirectories from those
explicit roots. The canonical detailed layout is [files and state](../documents/reference/files_and_state.md).
Immutable binary/artifact directories contain version/digest identity; the private psmux registry remains stable
across revisions. Rust/Cargo/cache/temp paths are private. Native short build roots outside these parents are
registered with their nonce and verified absolute cleanup boundary, never silently excluded from containment.

On a Windows host, Linux build, state and storage stay on dedicated storage of the VirtualBox guest; the source
path is the bind mount of the live Windows checkout. Native host and guest can read the same inputs but never run
concurrent write-guarded checks against a changing tree. Verified runs write each half's receipt exclusively
outside the checkout at `<state>/validation/receipts/<phase>/<half>/<identity>/<seq>-<nonce>.json` (D-130).
