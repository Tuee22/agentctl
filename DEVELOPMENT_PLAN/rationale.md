# Design Rationale

**Status**: Reference only
**Supersedes**: N/A

> **Purpose**: Preserve request anchors, identify current decision precedence, explain the target architecture and retain concept-note provenance.

This file explains; it does not instruct. The phase files say what each phase builds, and
[development_plan_standards.md](development_plan_standards.md) says how the plan is governed. This is
the one plan file that names shapes the project does not build, because naming a rejected shape is
how a reader avoids reintroducing it. The request block and the decision rows are anchors that
requirement quotes and oracle provenance point at, so both are append-only: a later answer is
appended to the block, and a revised decision is a new row that names the row it revises.

## Current Decision Precedence

The originating request and original decision anchors preserve provenance; current behavior follows the
explicit user amendments below and the canonical contracts in documents. A retained planner premise does not
override a later user instruction. Rows are append-only; phase numbers, phase filenames and committed closing
sprints are fixed, so a later decision re-homes an obligation to its owner instead of renumbering.
No retained old acceptance row qualifies the revised contracts.

## Design Justification

### Minimal bootstrap and Haskell-owned runtime

Python must exist before the first Haskell executable, so it performs verified toolchain/bootstrap build and
raw transport only. Runtime platform decisions, backend source/build preparation and actual session/recovery
behavior have one Haskell owner. Runtime consent crosses the handoff separately from the untouched agent tail.
Agent installation/login are outside this application even though native build tools and the multiplexer are
provisioned by their proper layer.

### Qualified native backends

Debian tmux comes from APT under the runtime consent plan. Windows psmux is a locally built private artifact
from pinned official source, exact patches and a locked native toolchain recipe. The candidate source includes
the client-frame coalescing and one-shot followup, but has no automatic acceptance merely because it is pinned.
Memory, control-event preservation, exact missing-target handling, wide wraps and conditional input are native
qualification obligations. Source-specific bytes belong to their concrete profile consumer; the reusable
builder's earlier closure covers its own complete algorithm and tested recipe contract.

A private Windows registry prevents collisions with system sessions and aliases. Replacing a client executable
updates no running process. Adoption of external endpoints is explicit; compatibility does not imply ownership
or permission to inject recovery input.

### Honest observation and delivery

Input safety needs coherent text/styles/cursor/dead/identity and a concrete server-ordered guard.
Separate CLI reads or two matching cursor positions cannot prove that no content changed. The Debian tmux
implementation must qualify sufficient actual native primitives; if that is not possible, the phase stays
incomplete until an adequate implementation is proven. The plan chooses neither a guessed join algorithm nor
an unvalidated replacement backend to hide the gap. Terminal ordering evidence states its domain and cannot
reveal hidden internal work in an agent.

### Independent evidence without partial testing

Every present test remains visible and executes where its host contract permits. Current independent receipts
cover each phase's owned inputs and actual prerequisites. Later-owned product or independently attributable
collection failures remain failures of that owner; common collection corruption, tampering or leaked
unregistered resources invalidate affected receipts. Missing future tests cannot supply evidence or block an
earlier complete scope. The overall result remains a complete checkout result, and final acceptance requires
every current native receipt and an empty ledger.

### Dedicated Linux validation on Windows

A dedicated Debian VirtualBox VM supplies the `linux`, `linux-clean` and `linux-live` halves without requiring
a committed transfer. The binder attaches the live checkout, verifies the guest's nonce answer and census,
writes the guest binding receipt and transports stored receipts, so the guest validates the same source tree
as the host. The VM is sized with host headroom from its observed CPU, memory, swap, virtual disk and
free-storage capacity; build, cache and state stay on dedicated Linux storage, and the source mount's
filesystem semantics are recorded as mount facts. Cross-project isolation proof is not a prerequisite. Guest
agents use the host login through read-only credential shares. The guest cannot establish a native Windows or
Darwin result, and D-133 and D-134 retire the superseded binding route and its diagnostic observers instead of
migrating them to equivalent controls.

## Rejected Alternatives

- A prebuilt product/backend release dependency in place of the required local source build.
- Moving runtime Rust/psmux/tmux or agent policy into the Python bootstrap.
- Selecting system psmux by PATH or trusting its same-version client banner as server qualification.
- Switching global aliases, sharing the default Windows registry or silently restarting existing sessions.
- Installing agent CLIs or logging them in through agentctl.
- Accepting Ubuntu merely because APT or ID_LIKE=debian is present.
- Guessing soft wraps by concatenating full-width rows, or using cursor equality as atomic snapshot proof.
- Replaying uncertain input delivery or weakening forbidden-input cases to make a backend qualify.
- A global later-phase failure or whole-tree-only phase digest as a prerequisite for earlier closure.
- Hiding legacy source, skips, suppressions, expected failures or an alternate workflow runner.
- A copied/committed WSL checkout bridge, unbounded host memory experiments or global WSL shutdown.
- Native Windows and macOS as joint mandatory hardware for a phase.
- Human review, manual fixtures, prompts, commits or a clean tree as acceptance requirements.
- Treating a stored receipt's seal or digest as authentication that a past run happened.
- Reusing a kill, baseline or mutant outcome from another run.
- Hashing status cells, sprint tags or other progress text into a phase identity.
- Coverage exclusions or omissions in `pyproject.toml` in place of host-declared foreign sources.
- An authored regressed, awaiting or blocked status instead of one computed from verified runs.
- Renumbering phases to reorder work instead of re-homing obligations to their owners.
- An earlier phase that consumes code, tests or data owned by a later phase.
- Re-owning a shared data home to one phase instead of projecting its rows to their owners.
